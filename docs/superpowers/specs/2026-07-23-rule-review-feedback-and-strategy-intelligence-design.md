# 规则审核反馈与搜索策略智能化设计

## 目标

让非技术用户能够顺畅编辑规则、看懂岗位变化如何影响规则、明确知道按钮是否已响应，并让搜索战役生成从“简单关键词列表”升级为可解释、可执行、可验证的招聘搜索策略。

## 方案比较

### 方案 A：只修前端交互和提示词

优点是改动小。缺点是岗位变化分析不可追溯，搜索策略质量仍完全依赖单次模型输出，换一个岗位后容易再次变简单。

### 方案 B：结构化变化分析 + 混合模型 + 本地策略编译器（采用）

岗位变化先由 AI 输出结构化影响分析并持久化；整合新版本时同时输入变化原文和分析。搜索战役使用 DeepSeek V4 Pro 的高推理档生成策略，再由本地规则做覆盖、去重、预算、标签来源和宽窄顺序校验。候选人批量评分继续使用 V4 Flash。

优点是策略质量、可解释性和稳定性兼顾，Pro 只用于低频高价值任务，避免候选评分成本和时延大幅增加。

### 方案 C：所有 AI 操作统一改用 Pro

实现最简单，但批量候选评分成本约为 Flash 的三倍，吞吐上限更低；结构校验和搜索逻辑缺陷也不会因为换模型自动消失，因此不采用。

## 交互设计

### 规则编辑

- 六个规则栏目继续使用多行文本框。
- 输入中的换行必须原样保留；仅在保存新版本时再将非空行规范化为规则数组。
- 逗号仍可用于同一行的快速拆分，但按下回车不得立刻删除空行或把光标拉回上一行。

### 岗位变化

- 点击“分析并保存变化”后，按钮立即显示“DeepSeek 正在分析…”，顶部通知同步显示当前动作。
- DeepSeek 输出：
  - 一句话变化摘要；
  - 受影响栏目：硬条件、加分项、目标公司、目标职位、正面证据、明确反证、待确认问题；
  - 每个栏目的建议新增、替换或删除内容；
  - 需要人工确认的问题。
- 分析结果随变化记录持久化并展示，刷新页面后仍可查看。
- 点击“整合 N 条变化为新版本”时，按钮显示“正在整合 N 条变化…”。后端把变化原文和结构化分析一并交给 DeepSeek，并生成新的草稿规则版本。
- 成功后自动滚动/聚焦到规则版本栏目，显示新版本号和受影响栏目；用户仍需人工批准。

### 按钮反馈

- 所有按钮有可见按压态和键盘聚焦态。
- 所有异步动作在请求发出前显示：
  - 按钮处理中标签；
  - 禁止重复点击；
  - 页面顶部持续的动作通知和进度条。
- 成功通知使用明确结果，例如“已生成规则 v2，影响 3 个栏目”。
- 失败通知使用明确失败动作和可重试提示，不只显示原始错误码。
- 导航、筛选等同步按钮至少提供按压态；不伪装成异步进度。

## 数据与接口

新增 `JobChangeAnalysis`：

```ts
type JobChangeSection =
  | "constraints.hard"
  | "constraints.soft"
  | "companies.target"
  | "roles.exact"
  | "evidence.required"
  | "evidence.negative"
  | "questions";

type JobChangeAnalysis = {
  summary: string;
  impacts: Array<{
    section: JobChangeSection;
    action: "add" | "replace" | "remove" | "review";
    values: string[];
    reason: string;
  }>;
  questions: string[];
  model: string;
};
```

`job_change_notes` 增加 `analysis_json`。`POST /api/jobs/:jobId/changes` 改为异步分析后保存；返回值包含 `analysis`。旧记录以 `analysis: null` 兼容。

整合接口继续返回完整 `JobPack`，但给 DeepSeek 的 `changes` 改为 `{text, analysis}` 数组。

## 搜索策略智能化

### 模型分工

- 岗位变化分析、变化整合、搜索战役生成：默认 `deepseek-v4-pro`，开启 thinking，`reasoning_effort=high`。
- 候选人基础判断和 `searchFit`：继续 `deepseek-v4-flash`，维持高吞吐和低成本。
- 允许通过 `DEEPSEEK_STRATEGY_MODEL` 覆盖策略模型；默认值为 `deepseek-v4-pro`。

DeepSeek 官方当前同时提供 V4 Flash 与 V4 Pro，二者均支持 JSON 输出；Pro 成本更高、并发更低，因此只用于低频策略任务。旧的 `deepseek-chat` 和 `deepseek-reasoner` 名称将在 2026-07-24 停用。

### 生成协议

模型必须输出 4–8 个互补搜索假设，每个步骤说明：

- 目标人才池和为什么值得搜索；
- 使用哪个已批准标签或自由文本；
- 预期结果过多时添加的下一维条件；
- 结果为 0 时使用的替代词或换向方案；
- 预期命中证据；
- 与其他步骤的差异。

策略应优先采用：

1. 单一目标公司或宽职位核心作为种子；
2. 结果大于 40 时再添加一个已批准维度；
3. 结果 1–40 时开始读取；
4. 结果为 0 时换同义词或下一假设；
5. 已知空集合的严格超集不得再尝试。

### 本地质量门

模型输出必须经过确定性校验：

- 4–8 个非重复步骤；
- 至少一个公司方向和一个职位方向；
- 至少覆盖两个不同搜索维度；
- 角色、行业、城市和职能只能来自已批准规则或用户输入；
- 初始步骤最多一个维度，不能一开始就过度收窄；
- 每步限制 5–40，总预算不超过 150；
- 每个来源和替代方向可追溯；
- 不满足时由本地编译器补全，而不是直接接受简单结果。

## 错误处理

- 变化分析失败时不创建半成品记录，输入内容保留，按钮恢复可点击。
- Pro 超时或结构不合法时允许一次同模型结构修复；仍失败则显示可重试错误，不静默回退到未经分析的保存。
- 搜索策略不通过本地质量门时返回明确错误；不自动确认、不启动任务。
- 任何失败都必须结束按钮的处理中状态。

## 测试

- 客户端测试：回车保留、异步按钮标签、成功/失败通知、变化分析渲染。
- API 测试：分析后保存、刷新后保留、结构化分析进入整合输入、失败不落库。
- DeepSeek 测试：策略任务使用 Pro thinking high，候选评分仍使用 Flash。
- 战役测试：初始步骤单维度、公司/职位覆盖、重复和越权标签被修复或拒绝。
- 完整 `verify`、`lint`，随后在本机网站用亦邦岗位做交互验收。
